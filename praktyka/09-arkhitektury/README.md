# Практична 09. Архітектури: масштабування, яке можна виміряти

Тема 9 · до **8 балів** · практика — друга пара й початок третьої ·
з середини третьої пари — **кожен ділиться результатом**

Минулого тижня ви зламали припущення про мережу. Сьогодні — питання, заради
якого взагалі беруть кілька машин: **що дає друга копія служби, а що вона ламає**.

Архітектури тут не описують словами. Їх запускають і міряють.

## Що має бути наприкінці

- `praktyka/09-arkhitektury/zvit.md` — таблиця з чотирма конфігураціями
  й **числами**: запитів/с, медіана затримки, скільки записів у кожному журналі;
- у звіті названо, **де в кожній конфігурації живе правда** і **де вузьке місце**;
- вибір архітектури під заданий сценарій і умова, за якої ви його зміните;
- усе на GitHub, рядок із результатом — у чаті.

**Мінімум для зарахування** — кроки 0–2: заміряна одна копія під навантаженням
і дві копії за балансувальником, видно розбіжність журналів.

**Контрольні точки:** 12:30 — крок 0 · 12:50 — крок 1 · 13:10 — крок 2 ·
13:30 — крок 3 (кінець другої пари) · 14:00 — крок 6, `push` і рядок у чат ·
14:10 — ділимось результатами.

## Стенд

| Файл | Що це |
|---|---|
| `sluzhba.py` | копія служби. `--imya A` видно в кожній відповіді. `--robota-cpu N` — скільки процесорної роботи коштує запит. `--shovyshche PORT` робить копію **без стану** |
| `balansuvalnyk.py` | одна адреса для клієнтів, кілька копій за нею; роздає по черзі й раз на секунду перевіряє, чи живі |
| `shovyshche.py` | спільний журнал для всіх копій |
| `navantazhennya.py` | N клієнтів одночасно: запитів/с, затримки, хто скільки обслужив, стан кожного вузла окремо |

Усе локально, стандартна бібліотека. Ні Docker, ні інтернету.

⚠️ У всіх запусках нижче — `--robota-cpu 10000`. Це приблизно 10 мс
процесорної роботи на запит: без неї ви міряли б швидкість сокетів, а не
служби.

## Крок 0. Один вузол, один клієнт (10 хв)

Термінал 1:

```
python sluzhba.py --port 50007 --imya A --robota-cpu 10000
```

Термінал 2:

```
python navantazhennya.py --port 50007 --kliyentiv 1 --zapytiv 200 --vuzly 50007
```

✔ Приблизно **50 запитів/с**, медіана затримки близько **23 мс**, помилок нуль.
✔ `обслужили: A: 200` і `:50007 (A) — записів 200`.

Це ваша точка відліку. Один клієнт не завантажує службу — він чекає на відповідь,
потім шле наступний запит.

## Крок 1. Один вузол, більше клієнтів (15 хв)

Запустіть те саме для 1, 2, 4 і 8 клієнтів (`--zapytiv 50`, щоб роботи було порівну):

```
python navantazhennya.py --port 50007 --kliyentiv 8 --zapytiv 50 --vuzly 50007
```

✔ Пропускна здатність росте не безмежно: на 8 клієнтах — приблизно
**164 запити/с**, і далі майже не змінюється.
✔ А от затримка росте: медіана з 23 мс стає близько **48 мс**.

Запишіть у звіт обидві криві. Це і є «сервер — вузьке місце» в числах:
черга довшає, кожному чекати довше, а служба швидше не стає.

⚠️ Згадайте тиждень 3: усередині одного процесу Python потоки не рахують
паралельно. Вузьке місце вашої служби — **той самий GIL**, тільки тепер
це вже архітектурна проблема, а не мовна.

## Крок 2. Друга копія за балансувальником (15 хв)

Термінали 1 і 2 — дві копії:

```
python sluzhba.py --port 50007 --imya A --robota-cpu 10000
python sluzhba.py --port 50008 --imya B --robota-cpu 10000
```

Термінал 3 — балансувальник:

```
python balansuvalnyk.py --port 50000 --vuzly 50007 50008
```

Термінал 4 — навантаження **через балансувальник**:

```
python navantazhennya.py --port 50000 --kliyentiv 8 --zapytiv 50 --vuzly 50007 50008
```

✔ Приблизно **228 запитів/с** проти 164: приріст є, але **не вдвічі**.
✔ `обслужили: A: 200 · B: 200` — балансувальник роздав порівну.
✔ І головне:

```
  :50007 (A) — записів 200
  :50008 (B) — записів 200
```

**Двісті і двісті, а не чотириста в одному місці.** Ви щойно отримали дві
правди замість однієї. Клієнт, який спитає «скільки всього замірів?»,
отримає різну відповідь залежно від того, до якої копії потрапить.

✔ **Мінімум для зарахування — ви тут.** У звіті: обидва числа пропускної
здатності й обидва журнали.

## Крок 3. Вузол помирає (15 хв)

Запустіть довге навантаження й **на другій секунді закрийте термінал вузла B**
(`Ctrl+C`):

```
python navantazhennya.py --port 50000 --kliyentiv 8 --zapytiv 200 --taimaut 3 --vuzly 50007 50008
```

✔ Кілька запитів упаде — приблизно **10–15 із 1600**: це ті, що були
в польоті до B у момент смерті.
✔ Далі балансувальник побачить, що B не відповідає, і виключить його:
`[балансувальник] вузол :50008 — НЕ ВІДПОВІДАЄ, виключаю`.
✔ Пропускна здатність упаде до рівня одного вузла (~134 запити/с).
✔ ⚠️ А тепер найважливіше: `:50007 (A) — записів 1420`. Ті записи, що
прийняв B, **зникли назавжди** — вони жили тільки в його пам'яті.

Порівняйте з балансувальником, який не перевіряє живість:

```
python balansuvalnyk.py --port 50000 --vuzly 50007 50008 --bez-perevirky
```

✔ Половина запитів б'ється об мертвий вузол; на ноутбуці викладача
100 запитів ішли **28 секунд** замість 0,7 с.

## Крок 4. Копії без стану + спільне сховище (15 хв)

Зупиніть усе. Тепер правда житиме в одному місці.

```
python shovyshche.py --port 50020
python sluzhba.py --port 50007 --imya A --robota-cpu 10000 --shovyshche 50020
python sluzhba.py --port 50008 --imya B --robota-cpu 10000 --shovyshche 50020
python balansuvalnyk.py --port 50000 --vuzly 50007 50008
python navantazhennya.py --port 50000 --kliyentiv 8 --zapytiv 50 --vuzly 50007 50008 50020
```

✔ Обидві копії тепер кажуть **одне й те саме**: `записів 400` і там, і там,
бо обидві питають сховище.
✔ Пропускна здатність — приблизно **185–205 запитів/с** проти 228: зайвий
стрибок по мережі коштує близько **15 %**.
✔ Тепер копії **взаємозамінні**: убийте будь-яку — нічого не загубиться.

⚠️ І одразу поставте собі питання, на яке відповідатимете у звіті:
**що станеться, якщо померти сховищу?** Перевірте: зупиніть його й запустіть
навантаження ще раз. На ноутбуці викладача — **0 успішних із 40**, хоча обидві
копії служби живі й відповідають.

## Крок 5. Вибір під сценарій (15 хв)

Сценарій — один із двох, на вибір:

- **A.** Збір показань лічильників із 10 000 квартир, раз на добу, сплеском.
- **B.** Обмін файлами між студентами гуртожитку, цілодобово, файли великі.

У `zvit.md`:

1. Таблиця чотирьох ваших конфігурацій із числами (кроки 0–4).
2. Яку конфігурацію ви візьмете для свого сценарію й **чому саме числа**
   з вашої таблиці це підтверджують.
3. Де в обраній архітектурі **єдина точка відмови** — вона є завжди,
   питання лише де.
4. Що змусить вас змінити рішення: конкретна умова, а не «якщо стане більше».
5. Для сценарію B окремо: чи допоможе тут узагалі клієнт-серверна схема,
   чи це випадок для однорангової? Один абзац.

## Якщо щось пішло не так

| Що бачите | Що це означає | Що робити |
|---|---|---|
| `WinError 10048` | порт зайнятий старим процесом | закрийте зайвий термінал або візьміть інший порт |
| Пропускна здатність однакова для 1 і 8 клієнтів | `--robota-cpu` не заданий — служба нічого не рахує | додайте `--robota-cpu 10000` **усім** копіям |
| `обслужили: A: 400` при двох вузлах | навантаження йде в порт служби, а не балансувальника | `--port 50000` |
| Балансувальник пише «живих вузлів немає» | обидві копії закриті або не встигли піднятись | підніміть і зачекайте секунду — перевірка раз на секунду |
| Числа стрибають між прогонами | ноутбук зайнятий чимось іще | беріть мінімум із трьох прогонів, як усі 8 тижнів |
| Затримки величезні на 8 клієнтах | так і має бути | це і є черга: подивіться на 95-й відсоток |
